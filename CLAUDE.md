# YASAD

Self-hosted portal (Yet Another Simple Accessible Dashboard): each person sees one screen with the links their groups allow. Local accounts, OIDC, or both. AGPL-3.0.

Product decisions live in the maintainer's private wiki, page "Décisions en vigueur", child of "YASAD". It is the only up-to-date reference: read it before changing behaviour, and propose an update there when a decision changes. The sibling page "Journal et analyse (historique)" is history only (it still mentions Django, which was dropped); never take a decision from it.

GitHub issues describe the need and the acceptance criteria, not the solution. Technical choices come from the decisions page and from this file.

Design specs (conception pages) are written in that wiki, as children of "YASAD", never committed to the repo.

The repository is public: never put the wiki's address, a link to one of its pages, or its content in a commit, a PR, an issue, a comment or a committed file.

## Layout

- `backend/`: Hono API, Drizzle (SQLite), Better Auth.
  - `src/app.ts`: runtime-agnostic app. Everything shared goes here or below. Each entry passes `getDb`, `getRawConfig`, `getClientIp` and `runtime` (`"docker"` from `server.ts` and the Node harness, `"workers"` from `worker.ts`), set in `c.var.runtime`.
  - `src/version.ts`: the build version (`__APP_VERSION__`, `dev` otherwise), `SOURCE_REPOSITORY` (the only place the repository address lives) and `sourceRefOf`/`sourceLinksOf` (anchored forms only: `git describe` output, a bare sha or a release; anything else links to the repository).
  - `src/config.ts`: environment validation, shared by both entries. `src/auth.ts`: Better Auth, mounted on `/api/auth/*`, public sign-up disabled.
  - `src/security.ts`: security headers (CSP and others) and the same-origin check on state-changing requests. `frontend/public/_headers` is generated from it for the Worker's static assets; a test fails when they drift.
  - `src/access.ts`: the only place the visibility rule lives. `viewerGroupIds` (subquery of the groups a viewer holds), `linkVisibleWhere` (the condition on the `link` and `category` columns of a join, written once), `visibleCatalog` and `emptyState`; for the favourites, `visibleLink` (an `exists` usable without FROM, in `failWhen` guards), `visiblePins` (ids in `(position, link_id)` order) and `visiblePinCount` (scalar subquery for the cap). A pin whose link the person no longer sees keeps its `user_link_pin` row and position but is never sent nor counted. OIDC memberships are ordinary `user_group` rows to `oidc` groups, rewritten at each sign-in, so this file needs nothing for them; never filter links again in a route.
  - `src/icons/`: `resolve.ts` maps a catalog `icon` value to a served icon or null; `names.ts` is generated by `scripts/generate-icons.mjs`, never edited by hand.
  - `src/oidc.ts`: the OIDC Better Auth instance (`genericOAuth`), built by `oidcAuth()` only for the start and callback routes (it returns null, hence `provider_unavailable`, when the provider Better Auth built lacks the issuer or signing algorithms YASAD read): discovery is read first with a timeout, account key `<iss>|<sub>`, claims checked in `validateUserInfo`, groups and role written by the session hook in one `db.batch` (`json_each`, constant parameters). The same batch sets `group.seen_at` for every group of the token (the last time the provider sent it); groups created by the catalog edit or the import keep it null, and `GET /api/admin/groups` exposes it as `seenAt`. The common instance of `auth.ts` never loads the plugin; both share `sharedOptions()`.
  - `src/routes/`: YASAD routes; errors use `apiError()` (`{ error: { code, message } }`). `admin-users.ts` and `admin-groups.ts` are the admin screens' API; the last enabled local admin is checked inside the write, not before it. `routes/auth.ts` is the allow-list of Better Auth routes (sign-in limits, `PASSWORD_SIGN_IN`); any other `/api/auth/*` path answers 404. Add a Better Auth route there only when the app uses it. The OIDC start ignores its body except a same-origin `returnTo` (an `idToken` in the body would sign in without the code flow), and the callback wrapper only lets known error codes through to `/sign-in?error=`. `routes/account.ts` is the signed-in user's profile and password: name and e-mail edits for local accounts only (a new e-mail needs the current password, counted like a password change), and a password change clears `must_change_password` and closes the account's other sessions. `routes/setup.ts` is the first-run setup (setup code checked and counted before the admin is created; 404 once closed). `routes/instance.ts` is `GET /api/instance` (title, logo the CSP can show, theme). `routes/about.ts` is `GET /api/about` (`requireUser`, `private, no-store`, no database read): `version` and `source` links for everyone, `instance` (`runtime`, `catalogManagedByFile`, never the path) for an admin only; the body is an allow-list, tested by strict equality. `routes/home.ts` is `GET /api/home` (public, `Cache-Control: private, no-store`; `pins` lists the viewer's visible pins, `[]` when anonymous). `routes/pins.ts` is `/api/pins` (POST `{linkId}`, DELETE `/:linkId`, POST `/:linkId/move` `{direction}`), behind `requireUser` (`routes/require-user.ts`: any signed-in role, 401 `unauthenticated` otherwise), never behind `requireAdmin` nor `catalogWritable`: each gesture is one `db.batch` with `failWhen` guards inside `retrying()`, answers `{ pins }`, and gives the same 404 `not_found` for a missing, inactive or forbidden link, checked before the cap (`MAX_PINS = 20` visible pins, 409 `pins_full` with `{ max }`). A new pin takes `max(position) + 1` over all the person's rows, hidden ones included; a move swaps with the next visible pin; positions are unique per person, not dense. Pins write no audit entry. `routes/viewer.ts` (`viewerOf`) reads who is asking from the session. `routes/admin-catalog.ts` exports and imports the catalog file, and `GET /api/admin/catalog/state` says whether `CATALOG_FILE` manages it. `routes/admin-links.ts` is the API of the catalog edits (`/api/admin/categories`, `/api/admin/links`): thin routes over `catalog/edit.ts`, every write refused with 409 `catalog_managed_by_file` under `CATALOG_FILE`, before the body is read (`catalogWritable`, shared with the import). `AdminLink` carries `check` and a read-only `status` (`state`, `reason`, `httpStatus`, `checkedAt`). Routes read a JSON body with `readJson` (`routes/body.ts`).
  - `src/audit.ts`: the admin action log. Snapshot SQL per object type (an allow-list of columns, never `account`, `session` or `verification`). `auditStatements()` returns the entry insert plus a purge of up to 100 expired rows, to put in the write's `db.batch`; an entry is written only when `after` differs from `before`. `unchangedSince()` and `failWhen()` (a NOT NULL insert, so it needs no anchor row) fail the batch; routes retry with `retrying()` when only the snapshot changed. Triggers (custom migration) refuse any update and any delete of an entry younger than 30 days. Never write to `audit_log` outside this file. `routes/admin-history.ts` is `GET /api/admin/history` and `/actors`, read-only. `AUDIT_RETENTION_DAYS` runs from 30 to 3650 days.
  - `src/server.ts`: Docker/Node entry (libSQL file, runs migrations at startup, serves `frontend/dist`).
  - `src/worker.ts`: Cloudflare Workers entry (D1 binding, static assets from `frontend/dist`).
  - `src/net/`: guarded outbound HTTP, no `node:*` import. `policy.ts` (`checkTarget`: `http`/`https` only, no credentials in the URL, reserved names, the Fetch bad ports; `isPublicAddress`: ipaddr.js `unicast` and outside `::/96`), `doh.ts` (fail-closed DNS-over-HTTPS resolution, CNAME chains up to 8 hops), `outbound.ts` (the `Outbound` interface, `OutboundError` and its codes, the headers sent, built from scratch), `classify.ts` (a result to `up`, `down` or `unknown`, or null for `not_attempted` and `too_large`: a platform error never becomes `down`), `fetch-outbound.ts` (`fetchOutbound`, used on Workers and in API tests: every address of the name validated, then `fetch` with `redirect: "manual"`, each redirect hop checked and resolved again, one deadline for the whole request).
  - `src/server-outbound.ts`: the Node implementation (`nodeOutbound`): resolves with `dns.promises.Resolver` and pins the validated addresses through a `lookup` hook on dedicated agents (no second resolution, no proxy). The only Node-only file besides `server.ts`, imported by `server.ts` alone (and by `test/server/`).
  - `src/catalog/`: catalog file format (`format.ts`, YAML and zod), groups by (source, name) (`groups.ts`; OIDC sign-in writes its groups in `oidc.ts` under the same unique key) and the diff and single-batch apply (`sync.ts`). Example in `docs/catalog.example.yaml`, checked by a test. `edit.ts` holds each admin gesture on a category or a link: it validates with the schemas of `format.ts` and returns `{ statements, before, afterOf, failureOf, warnings }` without running anything; `applyEdit` runs the statements in one batch. Each PATCH and DELETE sends the item's `revision` (bumped by every write in the app, not by a move made in the app; an import bumps every item whose content or rank changes), checked by a `guard()` in the batch, as are the local and system groups referenced, the format's limits, the link count of a deleted category and, for a move, that the item is still in the list it is moved in; after a failed batch, `failureOf` reads again to answer `not_found`, `item_changed` (with `current`), `unknown_group`, `unknown_category`, `id_taken` or `catalog_full`, or `"retry"` when an id derived from the title was taken meanwhile (`applyEdit` derives it again). `warnings` (`no_group`, `unknown_icon`, `groups_differ_by_case`, `new_oidc_group`, `check_blocked_address`, `check_blocked_port`, `check_login_gateway`; the last three static, from `checkTarget` and a closed list of Okta domains, no DNS) go back with a write that went through. `link.check` (column `check_enabled`, the property must stay `check`: `updateLink` spreads the body into `.set()`) marks a link for status checks; the result lives in `link_status` (one row per (link, source), `yasad` for the built-in checks), never in `revision` nor in the audit log; an edit or an import that changes the URL or unchecks the link deletes its `yasad` row in the same batch (the import's conditional delete comes before the upsert), and deleting a link cascades. Positions stay dense (0..n-1): a move, a deletion and a change of category renumber the list in the same batch, computed in SQL (`update ... from` with `row_number()`), because the import compares items by rank.
  - `drizzle/`: generated SQL migrations, one set for both targets.
- `scripts/generate-icons.mjs`: builds the catalog icons from simple-icons and lucide-static: `frontend/public/icons/<hash>/` (git-ignored, with NOTICE.txt), `frontend/src/icons-base.ts` and `backend/src/icons/names.ts` (both committed, never edited by hand).
- `frontend/`: React, Vite, Tailwind, shadcn/ui. In dev, Vite proxies `/api` to the backend on :3000.
  - `src/theme/themes/<id>.css`: one file per preset theme (`default`, `dusk`), defining every token in light and dark (only fonts, radii, tracking and heading weight may be left to the light block): shadcn variables, `--primary-shade`, `--selected` (selected-state marker), `--header*`, status colors (`success`, `warning`, `info`, `destructive`, each with `-foreground` and `-surface`), `category-1..6` and their `-fill` with `--on-fill`, controls (`--control-ring`, `--control-primary-ring`), `--link-decoration`, surfaces (`--panel-depth`, `--relief-highlight`, `--page-dot`, `--shadow-card`, `--shadow-raised`, `--radius-card`), `--heading-depth*`, fonts and heading style. A new token goes in every theme file and, when a utility class needs it, in the `@theme inline` map of `src/index.css`; `src/theme/theme-contrast.test.ts` checks the contract and the 3:1 and 4.5:1 pairs. Headings use the `text-display`, `text-title`, `text-section` utilities, meta text `text-caption`, pixel labels `text-pixel`; surfaces `panel`, `relief` (moves only without reduced motion), `sunken`, `pixel-corners`, `pixel-band`. Fonts are self-hosted from `@fontsource-variable/*` (OFL, credited in the README): Inter (body), Bricolage Grotesque (headings), Azeret Mono (captions, counts), Pixelify Sans (pixel accents). The wordmark uses Nabla, a latin subset kept in `src/fonts/` with its OFL and declared in `index.css`, because the Fontsource build drops its colour tables; do not replace it with the package. A theme's id must also be in `backend/src/themes.ts`, `src/preferences.ts` and `public/theme-init.js` (tests check all four); a removed id falls back to `default`.
  - `src/i18n/`: `en.ts` defines the messages, `fr.ts` must satisfy the same type. `useStrings()` in components; no hard-coded interface text.
  - `src/lib/router.ts` and `src/components/Link.tsx`: client-side routing (no dependency). Internal links use `Link`; each page sets its title with `useDocumentTitle` and gets focus on navigation. An API answer `unauthenticated`, `password_change_required` or `forbidden` reloads the session (`onStaleSession` in `api.ts`).
  - Widths: the app column (`COLUMN` in `components/AppShell.tsx`) is 1280 px for the header, the content and the footer; text pages use `Page width="reading"`, the account page `Page width="settings"` (1024 px, room for its two columns), and admin item pages are capped at 1024 px by `ITEM_WIDTH` (`DetailColumns`, the link and category pages).
  - Shared primitives: `PageHeader`, `SectionHeader`, `EmptyState`, `Brand`, `SkipLink`, `ui/alert`, `ui/badge`, `ui/button` (with `destructive`, `destructive-ghost` and `pending`). Forms use `components/form/` (`FormField`, `ErrorSummary`, `PendingButton`, `InlineForm`, `PasswordField`, `SelectField`, `FormLayout`), with API errors mapped by `lib/form-errors.ts` and status messages sent through `lib/announcer.tsx`. Use them rather than ad-hoc markup.
  - Administration: `components/admin/` (`AdminShell`: section links, page title, optional back link; `AdminToolbar`; `AdminTable`: a real table with sortable headers (`aria-sort`), one `RowLink` per row covering the row, tombstones in place; `DetailPage`: item pages whose back link and browser Back return the focus to the row (`rememberRow`, `listHref`, `useRestoreRow`), list filters kept in the URL (`useQueryState`); `Wizard`: numbered steps, focused step heading, `CheckList`, `Recap`; `StateMark`; `ConfirmPanel`; `SecretPanel`), `lib/admin-collection.ts` (`useAdminCollection`: load, retry, refresh, latest request wins) and `lib/admin-list.ts` (`useListFeedback`: status line, tombstones). A new admin screen builds on them: no modal, a list is a table whose rows open an item page, actions live on that page, additions go through a wizard, a success is announced without moving the focus, a deletion leaves a focused message in place of its row. Interface copy stays short and factual: help text only where it prevents a mistake. `pages/admin/links/`: the catalog screens (#32 behaviour): one table per category, `?q=` and `?state=noGroup|unknownIcon|neverReceived|inactive`, link and category pages showing the stored value under each field after `item_changed`, a reorder mode (categories or links) from the keyboard, read only under `CATALOG_FILE`, `invalidateHome()` after every write; the YAML import and export live at `/admin/links/file`. The change log is read in `pages/admin/history/` (`HistoryPage` with filters in the query, `HistoryTable` with one disclosure row per entry, `RecentChanges` on each item page); field names and value formatting per object type live in `history-format.ts`, and a new snapshot field needs a label in `history.fields` of both locales.
  - `src/lib/home-store.ts`: the one cached `GET /api/home` answer, keyed by viewer, shared by the home page and the header search. `App.refresh()` calls `invalidateHome()` on every session change; never register a second `onStaleSession` listener (`api.ts` keeps one, a second replaces App's). Call `invalidateHome()` after any admin change that alters what someone sees. A pin gesture patches the entry with `setHomePins(key, generation, pins)`, the generation read when the gesture was sent: a stale generation reloads the home of `key` without a reset, another viewer's entry is left alone. Pin gestures go one at a time, first in first out, through `useGestureQueue` (`lib/pin-queue.ts`); the pressed button is `pending` while queued or in flight.
  - `src/components/home/`: the home page. `PinsPanel` is the favourites aside (signed-in viewer with visible categories only), first in the DOM, right column from `lg`, sticky only on a screen wide and tall enough (`.pins-panel` in `index.css`). `pins-mode.ts` (`usePinsMode`) is the manage mode: never remembered, closed by a session change, Escape closes it unless already `defaultPrevented`, focus back to the toggle `pins-toggle`; while open it sets `html[data-pins-managing]` (scroll padding for the bar). `ManageBar` is the fixed bottom bar of that mode (`.pins-bar`, static on a low screen, a real border in forced colors). `LinkCard` shows its Pin button row only in that mode.
  - `src/pages/About.tsx`: the about page (`/about`, entry "About" of the account menu): version, source and licence for everyone, the instance's platform and catalog mode for admins. Links to the source and to the icons' `NOTICE.txt` are plain `<a>`, not `Link`. Its credits come from `src/lib/credits.ts` (fonts and icon sets, names and licences not translated): a new `@fontsource-variable/*` font, vendored font or icon set needs an entry, and `credits.test.ts` checks it against `package.json` and `index.css`.
  - `src/lib/search.ts`: client-side matching (folding, word prefixes, hyphen joining, ranking) over the visible links and their keywords. `src/components/search/`: the header combobox, `/` and Ctrl/Cmd+K.
  - `src/components/ui/`: shadcn components, copied (`components.json`). `public/theme-init.js` sets theme, mode and language before the first paint.
  - `e2e/`: Playwright and axe against the built Docker entry, every theme in light and dark, at 320 px and 1280 px. The `about` project covers the about page (axe in every theme, mode and width, a user without the instance section, the account menu entry, 320 px in French). The `pins` project covers favourites, set through the API as a dedicated local user and removed after each test. The `oidc` project runs a second server (OIDC only) against `fake-oidc-server.ts`, which serves `backend/test/harness/fake-oidc.ts`, the same fake provider the API tests plug into `fetch`.

## Commands

- `npm run dev`: backend (:3000) and frontend (Vite) together. Needs `backend/.env` (copy `backend/.env.example`).
- `npm run lint`, `npm run typecheck`, `npm run build`.
- `npm test`: the API tests in `backend/test/api/` run twice, on libSQL (`test:node`) and inside workerd on D1 (`test:workers`). Write API tests against `testApp(env)` from `#harness` (fresh database, cookie jar, config overrides), never against a specific driver. Node-only tests live in `backend/test/server/` (real `server.ts` process) and `backend/test/unit/`; frontend tests (Vitest, Testing Library) next to the components.
- `node scripts/generate-icons.mjs`: regenerates the icons (runs on the frontend `predev` and `prebuild`). Commit `backend/src/icons/names.ts` and `frontend/src/icons-base.ts` after bumping simple-icons or lucide-static; CI runs it with `--check`. lucide-static must stay on the version of lucide-react (a test checks it).
- `npm run db:generate --workspace backend` after any change to `backend/src/schema.ts`; commit the migration (CI fails otherwise).
- `npm run build:worker --workspace backend`: Worker bundle dry run.
- `npm run deploy:worker --workspace backend`: deploys the Worker with the version from `git describe --tags --always` (`backend/scripts/deploy-worker.mjs`, wrangler run without a shell; arguments after `--` go to `wrangler deploy`). Never run it from a test.
- `npm run test:e2e --workspace frontend`: builds the frontend, starts `server.ts` on :3199 with a fresh database and runs the browser tests (`npx playwright install chromium` once).
- `AUTH_SECRET=... SETUP_CODE=... docker compose up --build`: production image on :3000.

## Rules that must hold

- Two targets, one code: no Node-only API (`fs`, `child_process`, timers for background jobs) outside `server.ts` and `server-outbound.ts` (which only `server.ts` imports); no filesystem writes; scheduled work goes through a function both entries can trigger.
- Every outbound request to an address from the catalog or a user goes through `src/net/` (target policy, then pinned or validated resolution); never call `fetch` on such an address directly.
- Atomic writes use `db.batch([...])` (works on D1 and libSQL). Never `db.transaction()`: D1 does not support it. A check that must hold under concurrent requests goes inside the write (a `where exists` condition, or a guard statement in the batch), then the result is read back.
- Foreign keys are enforced on both targets: deleting a user or a group relies on `ON DELETE CASCADE` for sessions, accounts, memberships and catalog links.
- Access is deny by default. A link is visible only if the user holds a group on the link AND on its category (dashboards, when they come, will join the intersection). `@everyone` and `@authenticated` are system groups. Groups carry a `source` (`oidc`, `local`, `system`); an OIDC group never matches a local group of the same name.
- Filtering happens on the server; forbidden links never reach the browser, including through the API. Every access rule needs a test that calls the API directly.
- OIDC groups are written server-side from the verified ID token (Better Auth hook), never from user-editable fields.
- No automatic linking between a local account and an OIDC account sharing an e-mail.
- State-changing requests (POST, PUT, PATCH, DELETE), Better Auth routes included, must send a JSON body and come from PUBLIC_URL's origin. The CSP allows no inline script or style and no third-party origin: widen it in `security.ts` only, with the reason in the PR.
- WCAG 2.2 AA; keyboard navigation must work everywhere.
- Components use theme tokens only (`bg-background`, `text-primary`, `border-input`...), never raw Tailwind colors, so a theme can be swapped without touching them. One exception: purely decorative pixel art (`PixelScene`) keeps its own palette, provided it is `aria-hidden`, hidden in forced-colors mode and carries no text; anything read on top of it sits on a token-coloured plate. A new theme must pass the E2E axe run in both modes.
- The API returns error codes, never sentences meant for display; the frontend translates them.
- A user with `must_change_password` gets 403 `password_change_required` on every API route outside the short list in `app.ts`. New routes are covered automatically; do not add to that list without a reason.
- Radix components that inject `<style>` (modal menus, Select, Dialog scroll lock) break the CSP: use non-modal variants or native elements. The E2E fails on any CSP violation.

## Conventions

- Code, comments, commits and the README in English. Wiki pages in French.
- Branches `type/issue-topic` (e.g. `feat/12-oidc-login`), PR to `beta`, squash merge. `beta` is promoted to `main` by a PR merged with a merge commit (never squashed: semantic-release must see every commit, and `beta` must stay an ancestor of `main`).
- PR titles follow Conventional Commits (`feat:`, `fix:`, `chore:`...): semantic-release derives the version from them and publishes a git tag and a GitHub release (the release notes are the changelog). A merge into `beta` only builds the `beta` and `sha-` images; a numbered prerelease is published by running the CI/CD workflow by hand on `beta` (at the end of a batch of work), and a stable version by the promotion to `main`. No version commit, no `CHANGELOG.md`: `package.json` stays at `0.0.0-development`, and the version is injected at build time (`APP_VERSION`).
- Versions stay in 0.x for now: versioning starts from the `v0.0.0` tag, `feat` and `fix` bump the patch, a breaking change bumps the minor (`.releaserc.json`). The `beta` to `main` PR that closes a milestone is titled `release: <milestone>` (e.g. `release: v0.1 core`) and bumps the minor too. Work only on the active milestone (the oldest open one); the roadmap lives in the wiki, page "Roadmap et milestones". Going to 1.0.0 is a deliberate change of those rules.
- Node 24 (`.nvmrc`). TypeScript stays on 6.0.x until typescript-eslint supports 7.
